# Manual move-in examples

These files are explicitly synthetic examples for tests or a deliberate manual import. They are never loaded into a running installation automatically. They describe no real customer, invoice or support ticket.

The kit is **Account, billing and support JSON v1**. It accepts one JSON object with an `accounts` array of 1–50 accounts, and an installation holds at most 500 accounts. IDs are stable, case-sensitive identifiers of 1–64 letters, digits, underscores or hyphens. Every account requires `id`, `name`, `renewalDate`, `noticeDays`, `renewalEvidence`, `billing`, and `support`. Dates are real calendar dates in `YYYY-MM-DD` form. Money uses nonnegative integer minor units for AUD, CAD, EUR, GBP, NZD or USD. Credits plus allocated payments cannot exceed the invoice total. Observation dates cannot be in the future. Ticket counts are nonnegative integers, with urgent tickets no greater than open tickets. `noticeDays` is an integer from 0 through 3650.

`accounts-synthetic.json` includes referenced billing and support observations. `accounts-unknown-synthetic.json` deliberately uses `null` for both observations: null means unknown, never zero, paid or healthy. Billing fields describe the exported snapshot; the import does not contact a billing or support provider.

Preview the exact upload first. Confirmation must supply the returned fingerprint and a stable operation key with the same accounts. Changing an account, evidence or observation invalidates that approval. Repeating the same operation key and reviewed source resumes or returns the same durable import job. A kit response in `applying` or `undoing` is resumable; repeat the same apply or undo call until completed. A different upload cannot reuse the same operation key.

The source hash covers canonical JSON of the complete normalized upload, including IDs and evidence. The journal retains normalized source, mapping and custody, rather than original uploaded bytes; original-byte unavailability is visible in preview diagnostics. Caller operation keys are hashed before retention. No provider credentials or executable connector settings belong in these files.

Undo is strict: a native edit or dependent proposal, task, decision or event prevents reversal. The import only creates new accounts; conflicting existing accounts are refused rather than overwritten. Erasure is owner-only and atomically removes the native account, cascading product dependencies, and redacts its retained import source/evidence. Permanent hashed target and source tombstones prevent a new import from resurrecting erased records. Native account creation must fence `notErasedSql(id)` in its own authorized write transaction as well.

The Worker import-kit production dependency closure is reused unchanged from Base commit `fc0e1041efa55771142bbb57c4ab4743147e264d`, rooted at `modules/import-kit/src/d1/index.ts`. Its fresh D1 schema comes from Base migrations `0018_import_kit.sql`, `0020_import_erasure_append_only.sql`, `0021_import_preparation_steps.sql`, and `0022_import_stream_sources.sql`, with product capacity and permanent-tombstone triggers added. No Base proof or test code is copied.
